# แผนการทำงานของเว็บแอป — Talat Tha Na Map

*[Read in English](webapp-plan.md)*

แผนการทำงานเชิงฟังก์ชันและเทคนิคของระบบ อ้างอิงจากข้อเสนอโครงการ
([CEP_ข้อเสนอโครงการ.md](../CEP_ข้อเสนอโครงการ.md)) และโครงสร้างที่มีอยู่แล้วใน
`frontend/`, `backend/`, และ `tools/` ส่วนใดที่ข้อเสนอโครงการไม่ได้ระบุไว้ชัดเจน
จะทำเครื่องหมาย **[ข้อสันนิษฐาน]** กำกับไว้ — หากทีมต้องการแนวทางอื่น ควรตัดสินใจ
เรื่องเหล่านี้ก่อนเริ่มพัฒนาจริง

**หมายเหตุการทบทวนแผน**: การทบทวนรอบนี้อ่านแผนใหม่ในฐานะชุดของ "กระบวนการ" ที่จะ
เกิดขึ้นจริงในตลาดชุมชนอายุ 140 ปีที่ยังมีคนอยู่อาศัยและค้าขายจริง ไม่ใช่แค่ไดอะแกรม
ของระบบ การออกแบบที่สะอาดในเชิงเทคนิคยังสามารถสร้างปัญหาเดิมของตลาดขึ้นมาใหม่ในรูปแบบ
ดิจิทัล หรือสร้างความขัดแย้งทางสังคมแบบใหม่ขึ้นมาแทนที่ปัญหาเก่าได้ — พบจุดเช่นนี้อยู่
สี่จุด (การขอความยินยอมติดป้าย, POI ที่ข้อมูลล้าสมัย, ใครดูแลเนื้อหาหลังส่งมอบโครงการ,
และการนำข้อมูลวิเคราะห์ไปใช้เปรียบเทียบร้านค้า) ซึ่งระบุไว้แทรกในแต่ละหัวข้อด้านล่าง
พร้อมเพิ่มหัวข้อใหม่ §6

## 1. วงจรการใช้งานหลัก (Core loop)

1. นักท่องเที่ยวเดินไปถึงจุดที่น่าสนใจ (POI) — ร้านค้า, อาคารประวัติศาสตร์,
   หรือจุดติดตั้งงานศิลปะ — และพบสติกเกอร์ QR Code ที่ติดไว้ ณ จุดนั้น
2. สแกนด้วยกล้องมือถือ (ไม่ต้องติดตั้งแอปใด ๆ — ระบบจะเปิดลิงก์ผ่านเบราว์เซอร์ทันที)
3. ลิงก์จะพาไปยัง **หน้า check-in** ของ POI นั้น ๆ ซึ่งแสดงข้อมูล POI
   (ชื่อ, เรื่องราวประวัติศาสตร์/วัฒนธรรม, สินค้าที่ร้านนั้นจำหน่ายในกรณีที่เป็นร้านค้า)
   พร้อมทั้งบันทึก "ตราประทับดิจิทัล" (digital stamp) ของ POI นั้นให้กับ session
   ของผู้ใช้งาน
4. นักท่องเที่ยวสามารถเปิด **แผนที่** ได้โดยตรงเช่นกัน (ไม่ต้องสแกน) เพื่อสำรวจ POI
   ทั้งหมด ดูว่าจุดใดเก็บตราประทับไปแล้ว และเห็นภาพรวมว่ายังเหลือจุดใดที่ยังไม่ได้ไป
5. หน้า **สมุดสะสมตราประทับ / ความคืบหน้า** จะแสดงจำนวนตราประทับที่เก็บได้เทียบกับ
   ทั้งหมด ทำให้การเดินชมตลาดกลายเป็นเกมสะสมเล็ก ๆ ที่ชักจูงให้นักท่องเที่ยวสำรวจ
   ทั่วทั้งตลาด ไม่ใช่แค่บริเวณที่มีชื่อเสียงอยู่แล้ว

ส่วนนี้ตอบโจทย์ผลลัพธ์ที่คาดหวังทั้งสามข้อในข้อเสนอโครงการโดยตรง ได้แก่ ระบบนำทาง,
การกระจายเวลา (และการใช้จ่าย) ของนักท่องเที่ยวไปทั่วตลาด, และการสื่อสารเชิงวัฒนธรรม

**ข้อควรระวัง**: กลไกการสะสมตราประทับควรเป็นแบบที่ผู้ใช้กำหนดจังหวะเองล้วน ๆ —
ไม่มีตัวนับเวลาถอยหลัง, ไม่มีลีดเดอร์บอร์ดแบบเรียลไทม์, ไม่มีการจัดอันดับ "ผู้ที่เก็บ
ตราประทับมากที่สุดสัปดาห์นี้" ตลาดชุมชนขนาดเล็กและหนาแน่นไม่สามารถรองรับนักท่องเที่ยว
จำนวนมากที่แห่ไปยัง POI เดียวกันพร้อมกันเพื่อไล่ล่าคะแนนได้ การสำรวจแบบไม่เร่งรีบและ
กำหนดจังหวะเองต่างหากที่จะช่วยกระจายนักท่องเที่ยวได้จริง ซึ่งคือหัวใจของผลลัพธ์ที่
คาดหวังข้อ 1 กลไกใด ๆ ที่เปลี่ยนการสำรวจให้กลายเป็นการแข่งขันจะขัดกับเป้าหมายนี้โดยตรง

## 2. Frontend — หน้าและเส้นทาง (routes)

| Route | จุดประสงค์ |
|---|---|
| `/` | หน้าแรก: แนะนำตลาด, ลิงก์เข้าสู่แผนที่, จำนวนตราประทับปัจจุบัน |
| `/map` | แผนที่ตลาดแบบโต้ตอบได้ พร้อมหมุด POI ที่แสดงสถานะเก็บ/ยังไม่เก็บตราประทับ |
| `/poi/:poiId` | รายละเอียด POI (ประวัติ, ภาพ, สินค้าที่จำหน่าย) — เข้าถึงได้จากการเรียกดู ไม่จำเป็นต้องสแกน |
| `/checkin/:poiId` | ปลายทางของ QR Code — ตรวจสอบความถูกต้องของการสแกน, บันทึกตราประทับ, จากนั้นแสดงหน้ารายละเอียด POI เดียวกันพร้อมสถานะ "เก็บตราประทับสำเร็จ!" |
| `/stamps` | สมุดสะสมตราประทับ: ตาราง POI ทั้งหมด แสดงที่เก็บแล้ว/ยังไม่ได้เก็บ พร้อม % ความสำเร็จ |
| `/about` | ประวัติตลาดและเครดิตโครงการ (เนื้อหาจากส่วนหลักการและเหตุผลในข้อเสนอโครงการ) |

ปัจจุบัน `frontend/src/pages/` มีเพียงไฟล์ `.gitkeep` — หกหน้านี้คือเป้าหมายแรกที่ต้อง
พัฒนาจริง ส่วน `frontend/src/components/` ควรเก็บชิ้นส่วนที่ใช้ซ้ำได้ เช่น `MapPin`,
`POICard`, `StampGrid`, `StampBadge`

**การแสดงผลแผนที่ — [ข้อสันนิษฐาน]**: ใช้ภาพแผนที่ที่วาดขึ้นเอง (custom illustrated
map) ซึ่งสอดคล้องกับแนวทางศิลปะ/ภาพจิตรกรรมที่กล่าวถึงในข้อเสนอโครงการ โดยวาง POI เป็น
หมุดตำแหน่ง `{x%, y%}` ทับบนภาพ แทนที่จะใช้แผนที่ระบบพิกัด GPS จริง (เช่น Leaflet)
เนื่องจากตลาดมีขนาดเล็กและเป็นพื้นที่เดินเท้า จึงไม่จำเป็นต้องพึ่งความแม่นยำของ GPS
และแผนที่วาดเองยังเข้ากับงบประมาณด้านกราฟิก/โปสการ์ดที่ตั้งไว้มากกว่า หากทีมต้องการใช้
ตำแหน่ง GPS จริงแทน จะต้องเปลี่ยน data model ของ POI (เพิ่ม lat/lng) และเพิ่ม
dependency ด้าน map tile ซึ่งเป็นงานฝั่ง frontend ที่ใหญ่ขึ้น — ควรตัดสินใจเรื่องนี้
แต่เนิ่น ๆ

**ตัวตนผู้ใช้งาน — [ข้อสันนิษฐาน]**: ไม่มีระบบ login เมื่อเข้าใช้งานครั้งแรก
ฝั่ง client จะสร้างรหัสผู้ใช้งานแบบสุ่ม เก็บไว้ใน `localStorage` และส่งไปพร้อมทุกครั้ง
ที่ check-in วิธีนี้เพียงพอสำหรับติดตามว่า "เบราว์เซอร์นี้เก็บตราประทับของ POI นี้แล้ว
หรือยัง" และนับจำนวนผู้ใช้งานที่ไม่ซ้ำกันในการวิเคราะห์ข้อมูล โดยไม่ต้องเก็บข้อมูล
ส่วนบุคคล (PII) หากทีมต้องการกลไกของรางวัล/แลกของสำหรับผู้ที่เก็บครบทุกตราประทับ
(ยังไม่มีในงบประมาณปัจจุบัน แต่เป็นขั้นต่อไปที่เป็นไปได้) จุดนี้จะเป็นจุดที่ต้องเพิ่ม
การกรอกชื่อ/เบอร์โทรแบบสมัครใจ — ควรแจ้งให้ทีมทราบตั้งแต่ตอนนี้ เพื่อไม่ต้องย้อนกลับมา
แก้ไขภายหลัง ผลข้างเคียงหนึ่งที่ควรจับตา: ตอนนี้ `visitor_id` ไม่มีความหมายเชื่อมโยง
ถึงตัวบุคคลใด ๆ การส่งค่านี้เป็น query-string parameter (§5) จึงไม่มีปัญหา แต่ทันทีที่มี
ข้อมูลส่วนบุคคลผูกเข้ากับค่านี้ จำเป็นต้องย้ายออกจาก URL — เพราะ query string จะถูก
บันทึกใน server log และรั่วไหลผ่าน `Referer` header ได้ — ให้ย้ายไปอยู่ใน header หรือ
cookie แทน

**ความทนทานเมื่อออฟไลน์ — [ข้อสันนิษฐาน]**: `/map` และ `/poi/:id` ควรอ่านข้อมูลจาก
รายการ POI ที่ดึงมาครั้งเดียวแล้ว cache ไว้ฝั่ง client ไม่ใช่เรียก network ใหม่ทุกครั้งที่
เปลี่ยนหน้า ตลาดท่านาเป็นตลาดริมน้ำเก่าแก่ — ตรอกซอกซอยแคบ, สิ่งปลูกสร้างเก่าหนาแน่น,
ไม่มีสัญญาณที่รับประกันได้ — การออกแบบที่ต้องพึ่งการเชื่อมต่อเรียลไทม์เพื่ออ่านหน้า POI
แม้แต่หน้าเดียว จะล้มเหลวตรงจุดที่ต้องการใช้งานมากที่สุดพอดี มีเพียงการบันทึกข้อมูล
check-in (`POST /api/checkins`) เท่านั้นที่จำเป็นต้องมีการเชื่อมต่อจริง ณ ขณะนั้น —
ควรเก็บคำขอไว้ในเครื่องและลองส่งซ้ำเงียบ ๆ เมื่อสัญญาณกลับมา แทนที่จะบล็อกแอนิเมชัน
การรับตราประทับไว้เพราะรอสัญญาณ

## 3. รูปแบบของ QR Code

QR Code แต่ละอันของแต่ละ POI จะเข้ารหัส URL ในรูปแบบ:

```
https://<domain>/checkin/{poi_id}?t={poi_secret}
```

- `poi_id` ระบุว่าเป็น POI ใด
- `poi_secret` คือโทเคนสั้น ๆ เฉพาะของแต่ละ POI (สร้างขึ้นครั้งเดียว เก็บไว้พร้อมกับ
  ข้อมูล POI) เพื่อป้องกันไม่ให้นักท่องเที่ยวเดา URL เช่น `/checkin/2`, `/checkin/3`
  แล้วเก็บตราประทับโดยไม่ได้ไปที่จุดนั้นจริง ไม่จำเป็นต้องเข้ารหัสแบบซับซ้อนมาก — นี่คือ
  กิจกรรม walk-rally ไม่ใช่ระบบรักษาความปลอดภัยระดับสูง — เพียงแค่สร้างอุปสรรคพอที่การ
  พิมพ์ URL เองจะไม่ใช่ทางลัด
- `tools/qr-generator.html` (พัฒนาไว้แล้ว) สร้างไฟล์ QR/โลโก้ผสมสำหรับพิมพ์ จาก URL
  รูปแบบนี้ — ทีมงานนำลิงก์ `/checkin/{id}?t=...` ของแต่ละ POI มาวางแล้วพิมพ์ เครื่องมือ
  นี้ยังคงเป็นเครื่องมือแบบ standalone ที่ทำงานออฟไลน์ ไม่จำเป็นต้องเชื่อมต่อกับ backend

ขั้นตอนการ check-in ฝั่ง backend: `POST /api/checkins` ตรวจสอบ `poi_id` กับ `t`
เทียบกับ secret ที่เก็บไว้ จากนั้นบันทึก `(poi_id, visitor_id, timestamp)` หากโทเคน
ไม่ถูกต้องหรือขาดหายไป หน้า check-in จะยังคงแสดงข้อมูล POI ตามปกติ (เพื่อไม่ให้ลิงก์ที่
เสียหาย/ถูกคัดลอกทำให้ผู้ใช้งานเจอทางตัน) แต่จะไม่ได้รับตราประทับ

**การติดป้ายจริงเป็นการตัดสินใจเชิงสังคม ไม่ใช่แค่งานพิมพ์งานหนึ่ง** สติกเกอร์แต่ละอัน
เป็นของถาวรที่ติดอยู่บนอาคารหรือหน้าร้านของคนอื่น ในตลาดที่มีความพยายามปรับปรุงภูมิทัศน์
อยู่แล้ว (ภาพจิตรกรรมฝาผนังที่มีอยู่) ก่อนพิมพ์ ทุก POI ต้องได้รับความยินยอมเรื่องตำแหน่ง
และการออกแบบจากเจ้าของพื้นที่ และจากที่ปรึกษาด้านศิลปะของทีม — ไม่ใช่การตัดสินใจภายใน
ทีมพัฒนาแอปเพียงฝ่ายเดียว การข้ามขั้นตอนนี้เสี่ยงต่อความขัดแย้งแบบเดียวกับการติดป้ายโดย
ไม่ได้รับอนุญาตบนพื้นที่มรดกทางวัฒนธรรม และบั่นทอนความไว้วางใจที่โครงการต้องการจาก
ผู้ประกอบการตั้งแต่ก่อนเปิดใช้งานจริง

**โดเมนและ hosting ต้องอยู่ได้นานกว่าสติกเกอร์** งบประมาณครอบคลุมค่า hosting บน
เซิร์ฟเวอร์ของโรงเรียนเพียง 1 ปี แต่ QR Code ที่พิมพ์ออกมา (โดยเฉพาะรุ่นผลิตจริงบน
แผ่นอะคริลิคในขั้นตอนที่ 5 ของลำดับการพัฒนา) ถูกออกแบบให้อยู่ได้นานกว่านั้นมาก หากโดเมน
หมดอายุ หรือเซิร์ฟเวอร์ของโรงเรียนถูกปลดระวางหลังส่งมอบโครงการ สติกเกอร์ทุกอันในตลาดจะ
กลายเป็นลิงก์ที่ตายแล้ว — สร้างปัญหาเดิม "ไม่มีระบบนำทาง นักท่องเที่ยวสับสน" ขึ้นมาใหม่
ในรูปแบบที่พิมพ์บนอะคริลิคแล้วถอดออกเงียบ ๆ ไม่ได้ ผลที่ตามมาคือสองเรื่อง: (1) ใช้โดเมนที่
ชุมชน/โรงเรียนรับปากจะต่ออายุในระยะยาว ไม่ใช่โดเมนที่ผูกกับรอบงบประมาณของ CEP และ
(2) ตรวจสอบให้แน่ใจว่าหน้า check-in ยังคงแสดงข้อมูล POI จาก cache ได้แม้ backend/DB
จะล่มชั่วคราว เพื่อไม่ให้ปัญหา hosting ทำให้สติกเกอร์กลางตลาดใช้งานไม่ได้ — การล่มทั้งระบบ
คือความล้มเหลวรูปแบบเดียวที่นักท่องเที่ยวที่ยืนอยู่หน้าป้ายแก้ไขเองไม่ได้ จึงควรออกแบบ
รองรับไว้ตั้งแต่แรก

| `POI` | `id`, `name`, `category` (ร้านค้า / ประวัติศาสตร์ / ศิลปะ / อาหาร), `description`, `image_url`, `map_x`, `map_y`, `qr_secret`, `status` (active / closed / relocated) |

ปัจจุบัน `backend/app/models/` ยังว่างเปล่า — นี่คือเป้าหมายแรกที่ต้องพัฒนาฝั่ง
backend โดยน่าจะเป็น SQLAlchemy models ที่ผูกกับ `DATABASE_URL` ที่กำหนดไว้แล้วใน
`.env.example`

`status` มีอยู่เพราะการหมุนเวียนของร้านค้าในตลาดถูกบันทึกไว้แล้วในข้อเสนอโครงการเอง
(ร้านอาหารชื่อดังย้ายออกไป) หน้า POI และสติกเกอร์ที่พิมพ์ออกมาซึ่งยังคงอธิบายถึงร้านที่
ไม่มีอยู่แล้ว จะสร้างปัญหาเดิมขึ้นมาใหม่ในรูปแบบดิจิทัล — โดยไม่มีข้ออ้างเรื่อง "เดาไม่ถูก"
เหมือนครั้งก่อนอีกต่อไป `/api/pois` ควรตัดหรือทำเครื่องหมาย POI ที่ไม่ใช่ `active` ให้
ชัดเจน เพื่อไม่ให้แผนที่พานักท่องเที่ยวไปเจอทางตัน ดูหัวข้อ §6 ว่าใครมีสิทธิ์เปลี่ยนค่านี้
ได้บ้าง

**การเข้ารหัสข้อมูลเข้ามาเกี่ยวข้องตรงไหน**: `backend/app/crypto/encryption.py`
มีฟังก์ชัน encrypt/decrypt แบบ Fernet ที่พร้อมใช้งานอยู่แล้ว ควรใช้กับข้อมูลใด ๆ ที่
อาจระบุตัวตนบุคคลจริงได้หากฐานข้อมูลรั่วไหล — ภายใต้การออกแบบแบบไม่มี login ข้างต้น
ส่วนนี้แทบไม่มีเลย (ยังไม่มีชื่อ/เบอร์โทร) แต่หากทีมเพิ่มระบบแลกของรางวัลในภายหลัง
(ชื่อ/เบอร์โทร/LINE ID ของผู้ใช้งาน) คอลัมน์เหล่านั้นควรถูกเข้ารหัสก่อนบันทึกโดยผ่าน
helper นี้ใน `app/services/`

## 5. Backend API

| Method | Path | จุดประสงค์ |
|---|---|---|
| GET | `/health` | พัฒนาแล้ว |
| GET | `/api/pois` | รายการ POI ทั้งหมด (สำหรับแผนที่และสมุดสะสมตราประทับ) |
| GET | `/api/pois/{id}` | รายละเอียด POI เดียว |
| POST | `/api/checkins` | body `{poi_id, t, visitor_id}` — ตรวจสอบโทเคน, บันทึกตราประทับ, คืนค่าสถานะตราประทับล่าสุด |
| GET | `/api/checkins?visitor_id=...` | ตราประทับที่ผู้ใช้งานคนหนึ่งเก็บได้ (เพื่อให้หน้า `/stamps` ทำงานถูกต้องแม้ reload หน้า โดยไม่ต้องพึ่ง localStorage เพียงอย่างเดียว) |

`app/services/` เก็บ logic การตรวจสอบและบันทึกตราประทับ ส่วน `app/api/routes.py`
คงความเรียบง่าย (route → เรียก service) สอดคล้องกับแนวทางการแยกส่วนที่ระบุไว้แล้วใน
[PROJECT_STRUCTURE.th.md](../PROJECT_STRUCTURE.th.md)

หมายเหตุ: `GET /api/checkins?visitor_id=...` ส่ง `visitor_id` เป็น query parameter
— ไม่มีปัญหาตราบใดที่ยังเป็น UUID แบบไม่ระบุตัวตน (§2) แต่ควรทบทวนใหม่หากค่านี้เริ่ม
ถูกใช้เป็น key สำหรับค้นหาข้อมูลส่วนบุคคลใด ๆ และยังไม่มี `PATCH /api/pois/{id}` ในตาราง
นี้โดยตั้งใจ แม้ว่าจะต้องมีบางอย่างคอยเปลี่ยน `status` และแก้ไขเนื้อหา — ดู §6 ว่าทำไม
endpoint แบบ CRUD ตรง ๆ จึงไม่ใช่รูปแบบที่เหมาะกับคนที่จะมาแก้ไขข้อมูลจริง

## 6. วงจรชีวิตของเนื้อหา, ความเป็นธรรม และการส่งมอบ

สองกระบวนการที่แผนฉบับก่อนหน้ายังไม่ได้ครอบคลุม ทั้งสองเรื่องเป็นประเด็นทางสังคมก่อน
จะเป็นประเด็นทางเทคนิค

**ร้านค้าใดได้เป็น POI และร้านใหม่จะถูกเพิ่มเข้ามาได้อย่างไร** หากรายการ POI เริ่มต้น
เป็นเพียง "ร้านค้าสิบกว่าร้านที่ทีมบังเอิญถ่ายภาพไว้ระหว่างการลงพื้นที่ครั้งแรก" (§8
ขั้นตอนที่ 1) แอปจะสร้างปัญหาความไม่เป็นธรรมที่ผลลัพธ์ข้อ 1 ตั้งใจจะแก้ขึ้นมาใหม่โดยไม่รู้
ตัว: ผู้ประกอบการบางรายได้รับนักท่องเที่ยวเพิ่ม บางรายไม่ได้ โดยไม่มีเหตุผลที่มองเห็นได้
ทางแก้: ตกลงกฎเกณฑ์การคัดเลือกที่เรียบง่ายและเปิดเผยร่วมกับผู้ใหญ่บ้านที่ปรึกษาโครงการ
ก่อนที่รายการจากการลงพื้นที่ครั้งแรกจะถูกล็อกไว้ — เช่น "ร้านค้าทุกร้านที่ต้องการ QR Code
จะได้รับ" หรือกำหนดชุดที่หมุนเวียนอย่างชัดเจน — และเปิดช่องทางให้ผู้ประกอบการรายอื่นขอเข้า
ร่วมภายหลังได้ เนื่องจากรายการนี้จำเป็นต้องขยายต่อไปหลังส่งมอบโครงการอยู่แล้ว นี่เป็นเพียง
บทสนทนาสั้น ๆ ที่ทำตอนนี้เพื่อป้องกันปัญหาความน่าเชื่อถือในภายหลัง ไม่มีอะไรต้องพัฒนาเพิ่ม
สำหรับเรื่องนี้

**ใครเป็นผู้อัปเดตข้อมูล POI หลังทีมนักเรียนจบโครงการไปแล้ว** แผนความยั่งยืนในข้อเสนอ
โครงการระบุว่าจะส่งมอบระบบให้เทศบาลและมูลนิธิชุมชนหลังจากนั้น 1–2 ปี ตามการออกแบบ
ปัจจุบัน วิธีเดียวที่จะเปลี่ยน POI เป็น `closed`, แก้ไขคำอธิบายที่ผิด หรือเพิ่ม POI ใหม่ คือ
การเข้าไปแก้ไขฐานข้อมูลโดยตรง — ซึ่งหมายความว่าในทางปฏิบัติ มีเพียงคนที่เขียน backend
เท่านั้นที่ดูแลระบบต่อได้ นี่คือจุดล้มเหลวเดียว (single point of failure) ที่จะหมดอายุ
ในวันที่ทีมนี้จบการศึกษา และขัดแย้งโดยตรงกับการส่งมอบที่ข้อเสนอโครงการให้สัญญาไว้ ไม่จำเป็น
ต้องมี admin dashboard เต็มรูปแบบ — นั่นจะเกินความจำเป็นสำหรับทีมนักเรียน 8 คนและการส่งมอบ
ระดับหมู่บ้าน — แต่จำเป็นต้องมี "บางอย่าง" ที่คนที่ไม่ใช่โปรแกรมเมอร์ใช้งานได้ เช่น
สเปรดชีตที่แชร์กันไว้ แล้วมีสคริปต์เล็ก ๆ ซิงก์เข้าฐานข้อมูลตามรอบเวลาที่กำหนด ก็เพียงพอ
แล้ว และเข้ากับขนาดจริงของโครงการ ไม่ว่าจะใช้กลไกใด ควรบันทึกไว้เป็นรายการเฉพาะในเอกสาร
ส่งมอบ (ที่วางแผนไว้แล้วในขั้นตอนที่ 8 ของไทม์ไลน์ข้อเสนอโครงการ) ไม่ใช่รวมไว้เงียบ ๆ
ในหัวข้อ "นี่คือโค้ดทั้งหมด"

**ใครเป็นผู้ถือ `ENCRYPTION_KEY` หลังส่งมอบ** คือคำถามแบบเดียวกันในสเกลเล็กลง:
ตัดสินใจตั้งแต่ตอนนี้ว่าเทศบาล/มูลนิธิจะเป็นผู้ดูแลกุญแจนี้ หรือโรงเรียนจะเก็บไว้ในนามของ
ชุมชน เพื่อไม่ให้กุญแจนี้ตกค้างอยู่ในโน้ตบุ๊กเครื่องสุดท้ายที่มีไฟล์ `.env` ตอนที่ทีมจบ
การศึกษาไปแล้วเฉย ๆ

## 7. การวิเคราะห์ข้อมูล (post-processing)

ตอบโจทย์ตัวชี้วัดการประเมินผลในข้อเสนอโครงการโดยตรง:

- **เชิงปริมาณ**: จำนวนจุด POI ที่มี QR Code ใช้งานอยู่, จำนวนผู้ใช้งานที่ไม่ซ้ำกัน
  (`distinct visitor_id`), จำนวนการ check-in ต่อ POI ตามช่วงเวลา → ดูว่าจุดใดถูกข้าม
  ไป, รูปแบบการเคลื่อนที่ของนักท่องเที่ยว
- **เชิงคุณภาพ**: ส่วนนี้ไม่ได้อยู่ในระบบแอป — เป็นงานสัมภาษณ์/สำรวจความคิดเห็นตามที่
  ระบุในข้อเสนอโครงการ — แต่ `analytics/notebooks` ยังสามารถเก็บบันทึกสรุปส่วนนี้ควบคู่
  กับกราฟเชิงปริมาณสำหรับรายงานฉบับสมบูรณ์ได้

ข้อควรระวังสองข้อในการใช้ตัวเลขเหล่านี้ ทั้งคู่เป็นเพราะตัวเลขจะไปปรากฏในรายงานที่คนนอก
ทีมอ่าน: `distinct visitor_id` เป็นเพียงตัวแทนโดยประมาณของจำนวนผู้ใช้งานที่ไม่ซ้ำกัน
ไม่ใช่จำนวนหัวจริง — การล้าง localStorage และการใช้โทรศัพท์เครื่องเดียวกันร่วมกันในครอบครัว
ต่างบิดเบือนตัวเลขไปคนละทิศทาง — จึงควรนำเสนอเป็นค่าประมาณในรายงานประเมินผล ไม่ใช่ตัวเลข
ที่แม่นยำ ซึ่งจะทำให้การวัดผลของผลลัพธ์ข้อ 2 ตรงไปตรงมากับตัวมันเองมากขึ้น และจำนวน
check-in ต่อ POI ควรรวมกันเป็นภาพรวมเมื่อแชร์ออกนอกทีมพัฒนา: การจัดอันดับแบบเปิดเผยหรือ
กึ่งเปิดเผยว่า "ร้านไหนไม่มีใครไปเลย" จะเปลี่ยนเครื่องมือนำทางให้กลายเป็นแหล่งความขัดแย้ง
ระหว่างผู้ประกอบการ ซึ่งตรงข้ามกับเจตนารมณ์ของผลลัพธ์ข้อ 1 ควรใช้ข้อมูลแยกรายจุดนี้
ภายในทีมเพื่อวางแผนว่าจะเพิ่มป้ายหรือเนื้อหาตรงไหน ไม่ใช่นำมาใช้เป็นกระดานคะแนน

`analytics/scripts/` อ่านข้อมูลจากฐานข้อมูล Postgres เดียวกัน (แบบอ่านอย่างเดียว ตาม
กฎที่กำหนดไว้แล้วใน `PROJECT_STRUCTURE.md`) และ `analytics/notebooks/` ใช้สร้างกราฟ
heatmap การ check-in / funnel ความสำเร็จ สำหรับรายงานต่อผู้สนับสนุนโครงการ

## 8. ลำดับการพัฒนา (สอดคล้องกับไทม์ไลน์ ก.ค.–ก.ย. ของข้อเสนอโครงการ)

1. **ข้อมูล POI + หน้าแผนที่** — รายการ POI แบบ static (นำมาจากภาพถ่ายในการลงพื้นที่
   ครั้งแรก โดยใช้กฎการคัดเลือกที่ตกลงกันไว้ใน §6), หน้าแผนที่พร้อมหมุด, หน้ารายละเอียด
   POI ที่ cache ไว้ฝั่ง client ตาม §2 ยังไม่ต้องมี backend นอกจากการเสิร์ฟ JSON
   แบบ static
2. **ระบบ check-in** — โมเดล backend + `/api/checkins`, เชื่อมต่อ `/checkin/:poiId`,
   รหัสผู้ใช้งานใน localStorage, หน้าสมุดสะสมตราประทับ
3. **ทดสอบภาคสนามครั้งที่ 1** (QR Code แบบกระดาษ ตามข้อเสนอโครงการข้อ 3) — นำ URL
   `/checkin/{id}?t=...` จริงมาใส่ใน `qr-generator.html`, พิมพ์, ทดสอบหน้างานจริง
4. **ปรับปรุงตามผลตอบรับจากภาคสนาม**, ปรึกษาผู้ทรงคุณวุฒิครั้งที่ 2
5. **ติดตั้ง QR Code จริง** (ป้ายอะคริลิค) เมื่อระบบผ่านการทดสอบแล้ว และได้รับความยินยอม
   เรื่องตำแหน่งติดตั้งรายจุด (§3) เรียบร้อยแล้ว
6. **สรุปผลการวิเคราะห์ข้อมูลและส่งมอบ** — รายงานฉบับสมบูรณ์ พร้อมกลไกอัปเดตเนื้อหาแบบ
   ไม่ต้องใช้ทักษะโปรแกรมมิ่ง และการตัดสินใจเรื่องผู้ถือ `ENCRYPTION_KEY` จาก §6 ส่งมอบ
   ควบคู่ไปกับโค้ด ตามขั้นตอนที่ 8 ของการลงพื้นที่ในข้อเสนอโครงการ

## 9. ประเด็นที่ทีมต้องตัดสินใจ

- แผนที่วาดเองแบบภาพประกอบ vs. แผนที่ระบบ GPS จริง (ดูข้อ 2) — ส่งผลต่อ schema ของ
  POI และ dependency ฝั่ง frontend
- มีรางวัลสำหรับผู้ที่เก็บตราประทับครบทุกจุดหรือไม่? ส่งผลต่อการตัดสินใจว่าจะให้ตัวตน
  ผู้ใช้งานไม่เปิดเผยตัวตนทั้งหมด หรือต้องมีช่องกรอกข้อมูลติดต่อแบบสมัครใจ
- เนื้อหาสองภาษา (ไทย/อังกฤษ) — ข้อเสนอโครงการมุ่งเป้าไปที่นักท่องเที่ยวโดยรวม ควร
  ตัดสินใจตั้งแต่ตอนนี้เพราะส่งผลต่อฟิลด์เนื้อหาของทุก POI (`name_th`/`name_en` เทียบกับ
  ฟิลด์เดียว)
- เกณฑ์การคัดเลือก POI (§6) — ใครอยู่ในรายการแรก และผู้ประกอบการรายอื่นจะขอเข้าร่วม
  ภายหลังได้อย่างไร
- ความเป็นเจ้าของโดเมนและความต่อเนื่องของ hosting หลังปีแรกที่ได้รับงบประมาณ (§3) —
  ต้องมีผู้รับผิดชอบต่ออายุที่ชัดเจน
- ความยินยอมเรื่องป้ายรายจุด (§3) — ยืนยันกับร้านค้าแต่ละร้านและที่ปรึกษาด้านศิลปะ
  ก่อนพิมพ์ ไม่ใช่แค่ก่อนติดตั้ง
